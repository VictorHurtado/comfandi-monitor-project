# HU-009 — Actualización reciente de SonarQube, mensajes de error y validación QA

**Como** líder técnico y equipo de QA  
**Quiero** que los datos de Sonar se consideren recientes, que los fallos de conexión muestren un mensaje corto no técnico y que la carga no bloquee el dashboard  
**Para** confiar en el dashboard y poder validar fácilmente con proyectos buenos y malos

---

## Dependencias

- Requiere: HU-007 y HU-008 (tarjeta Sonar con Quality Gate y métricas)
- Esta HU no añade nuevas métricas; mejora actualización, resiliencia y documentación para validación.

---

## Contexto / Notas

- **Reciente**: se considera "reciente" un dato con una antigüedad máxima definida (ej. 5 minutos). Implementación típica: cache en BFF o en cliente con TTL, o revalidación al montar la tarjeta/entrar al dashboard. El intervalo concreto se fija en esta HU (ej. TTL 5 min) para que los agentes no inventen valores.
- **Mensaje si falla**: si la conexión a Sonar falla (timeout, 4xx/5xx, red), mostrar un mensaje corto y no técnico al usuario (ej. "No se pudo conectar con Sonar" o "Sonar no disponible"); nunca stack ni detalles de API.
- **Rendimiento**: la carga de la tarjeta Sonar no debe bloquear el resto del dashboard; cargar en paralelo con otras integraciones o de forma que la UI siga usable (loading por tarjeta, no pantalla completa).
- **QA**: documentar cómo validar la integración con un proyecto "bueno" (Quality Gate passed, métricas OK) y uno "malo" (failed o muchas issues), o con Sonar caído/no configurado, para que QA pueda repetir las pruebas.

---

## Alcance

**Incluye:**

- **Actualización reciente**: definir TTL de cache (ej. 5 minutos). Si el dato en cache es más viejo que el TTL, revalidar al mostrar la tarjeta o al entrar al dashboard. Opcional: indicador visual de "última actualización" (ej. "Actualizado hace 2 min") si el diseño lo permite.
- **Mensaje de error no técnico**: cuando la conexión a Sonar falle, la tarjeta muestra un mensaje corto (ej. "Sonar no disponible" o "No se pudo conectar con Sonar"); sin códigos HTTP ni mensajes de backend. Usar manejo de errores con `AppError` en capas inferiores y traducir en Presentation a mensaje de usuario.
- **Carga no bloqueante**: la petición a Sonar no bloquea el render del dashboard; loading por tarjeta o por integración; el resto de la página se muestra y las demás tarjetas cargan en paralelo.
- **Documentación para QA**: en `docs/close/hus/HU-004-taller/` o en `docs/close/`, añadir un documento breve (ej. `equipo-1-sonarqube-validacion-qa.md`) que describa:
  - Cómo validar con un **proyecto bueno**: proyecto en Sonar con Quality Gate passed y métricas en rango esperado.
  - Cómo validar con un **proyecto malo**: proyecto con Quality Gate failed o muchas bugs/vulnerabilities.
  - Cómo validar **fallo de conexión**: desactivar Sonar (env incorrecto o URL inalcanzable) y comprobar que se muestra el mensaje corto y la tarjeta no rompe el layout.

**No incluye:**

- Nuevas métricas ni cambios en el modelo de dominio de Sonar (salvo si hace falta un campo "lastChecked" para la UI).
- Integración con Jira ni otros proveedores.

## Criterios de aceptación (Given / When / Then)

### 1) Datos considerados recientes (TTL)

- **Dado** un TTL definido (ej. 5 minutos)
- **Cuando** el usuario ve la tarjeta Sonar y el último dato es más reciente que el TTL
- **Entonces** se muestran los datos en cache sin rellamada innecesaria; si el dato es más viejo, se revalida al entrar al dashboard o al mostrar la tarjeta

### 2) Mensaje corto y no técnico si falla la conexión

- **Dado** que la conexión a Sonar falla (timeout, error de red o API)
- **Cuando** el usuario ve la tarjeta de Sonar
- **Entonces** se muestra un mensaje breve y entendible (ej. "Sonar no disponible") y no se muestra ningún detalle técnico (códigos HTTP, stack, mensaje de backend)

### 3) Carga que no bloquee el dashboard

- **Dado** el dashboard con varias tarjetas (Sonar y otras integraciones)
- **Cuando** el usuario entra al dashboard
- **Entonces** la carga de Sonar no bloquea el resto; las tarjetas se cargan en paralelo o la de Sonar muestra loading propio sin congelar la página

### 4) Documentación para validación QA

- **Dado** el documento de validación QA para Sonar
- **Cuando** el equipo de QA sigue los pasos
- **Entonces** puede validar: (a) proyecto con Quality Gate passed y métricas OK, (b) proyecto con Quality Gate failed o muchas issues, (c) escenario con Sonar no disponible y mensaje correcto sin romper la UI

## Reglas técnicas

- Arquitectura: `docs/close/01_arquitectura.md`. Errores de dominio en Domain/Infrastructure; Presentation solo muestra mensaje de usuario.
- Errores: usar `AppError` y subclases; en Presentation detectar error y mostrar texto no técnico.
- Cache/TTL: puede implementarse en BFF (Next.js) o en cliente (React) con estado; no hardcodear intervalos sin documentarlos en la HU.
