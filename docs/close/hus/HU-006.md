# HU-006 — Integrar tarjeta Jira en Dashboard con métricas de flujo de trabajo

**Como** líder técnico  
**Quiero** ver la tarjeta de Jira en el dashboard de salud técnica del proyecto seleccionado  
**Para** revisar rápidamente el estado del trabajo (abiertas, bloqueadas, cerradas, tiempo en progreso) sin entrar a Jira

---

## Dependencias

- Requiere: HU-004 (cascarón UI del dashboard general)
- Requiere: layout y card de integraciones ya renderizados en `narnia/`
- Requiere: flujo de proyecto seleccionado desde `/project-selector` (la tarjeta muestra datos del proyecto en contexto)
- Opcional: configuración de Jira (URL, token). Si no está configurado o Jira está caído, mostrar estado `unknown` o `pending` sin romper la UI.

---

## Contexto / Notas

- La tarjeta de Jira se muestra en el dashboard de un **proyecto seleccionado** (ruta tipo `/dashboard/technical-health` con contexto de proyecto desde `/project-selector`).
- Jira se usa para seguimiento operativo y flujo de trabajo; la tarjeta debe dar lectura rápida de “cómo va el trabajo”.
- Respetar arquitectura por capas: Presentation → Use Cases ← Infrastructure. Domain define contratos; Infrastructure implementa cliente Jira/API.
- Si la integración falla o tarda mucho: estado `unknown`/`pending`, feedback visual (loading/timeout), **nunca** mensajes técnicos de backend al usuario ni tarjeta congelada sin feedback.
- Cambiar de proyecto debe actualizar los datos mostrados en la tarjeta (datos por proyecto).

- La tarjeta debe indicar a qué proyecto pertenece la información.
- Colores deben ayudar a entender si hay riesgo o no (p. ej. semáforo o tokens `brand-*`).
- Vacío = “sin issues” debe verse claro; no confundir con “fallo” o error.

## Alcance

Incluye:
- Tarjeta Jira en el dashboard general con **cuatro métricas**:
  1. **Issues abiertas** (cantidad)
  2. **Issues bloqueadas** (cantidad)
  3. **Issues cerradas en 7 días** (cantidad)
  4. **Tiempo promedio en estado "In Progress"** (horas, formato fácil de entender)
- Estados visuales: datos OK, vacío (sin issues), `unknown`/`pending` cuando Jira no está disponible o falla.
- Loading y timeout: si tarda mucho, mostrar feedback (spinner/skeleton o mensaje corto), no dejar la tarjeta congelada.
- Datos ligados al proyecto seleccionado: cambiar de proyecto actualiza la data de Jira en la tarjeta.
- Traducción de errores: no exponer mensajes técnicos de backend al usuario; usar mensajes amigables (ej. “No disponible” / “Pendiente”).

No incluye:
- Configuración de credenciales/tokens en esta HU (asumir variable de entorno o configuración existente si la hay).
- Edición de issues ni acciones dentro de Jira desde el dashboard.

## Criterios de aceptación (Given / When / Then)

### 1) Tarjeta Jira con lectura rápida del trabajo

- **Dado** el usuario en el dashboard de salud técnica con un proyecto seleccionado
- **Cuando** se renderiza la sección de integraciones
- **Entonces** se visualiza una tarjeta Jira que comunica rápidamente cómo va el trabajo del proyecto (métricas visibles sin entrar a Jira)

### 2) Métricas visibles: abiertas, bloqueadas, cerradas en 7 días, tiempo en "In Progress"

- **Dado** un proyecto con datos Jira disponibles
- **Cuando** se renderiza la tarjeta
- **Entonces** se muestran: issues abiertas (cantidad), issues bloqueadas (cantidad), issues cerradas en 7 días (número), tiempo promedio en "In Progress" (horas, formato legible)

### 3) Vacío vs fallo

- **Dado** un proyecto sin issues (Jira devuelve cero en las métricas)
- **Cuando** el usuario visualiza la tarjeta
- **Entonces** se ve claro que está vacío y no que falló la integración

### 4) Colores / riesgo

- **Dado** la tarjeta Jira renderizada
- **Cuando** el usuario la revisa
- **Entonces** los colores (tokens `brand-*` o semáforo) ayudan a entender si hay riesgo o no

### 5) Jira no disponible

- **Dado** Jira caído o no configurado
- **Cuando** se intenta cargar la tarjeta
- **Entonces** se muestra estado `unknown` o `pending` con mensaje amigable y el dashboard sigue operativo

### 6) Datos por proyecto

- **Dado** el usuario en el dashboard
- **Cuando** cambia el proyecto seleccionado
- **Entonces** la data de la tarjeta Jira se actualiza según el nuevo proyecto

### 7) Sin mensajes técnicos ni tarjeta congelada

- **Dado** un error de backend o respuesta lenta
- **Cuando** se muestra la tarjeta
- **Entonces** no se muestran mensajes técnicos de backend al usuario y, si tarda mucho, hay feedback (loading/timeout), no tarjeta congelada

### 8) Aislamiento de fallo

- **Dado** que la integración Jira falle o esté en timeout
- **Cuando** se renderiza el dashboard
- **Entonces** el fallo de la tarjeta Jira no rompe el resto del dashboard (QA puede validar este caso)

## Reglas técnicas

### Arquitectura
- Presentation solo consume Use Cases; no llamar APIs de Jira desde UI.
- Domain: modelos/contratos para métricas Jira (abiertas, bloqueadas, cerradas 7d, tiempo promedio In Progress); Use Case que expone “obtener métricas Jira por proyecto”.
- Infrastructure: implementación que llama a Jira (o BFF) y mapea respuestas a modelos de dominio; manejo de errores y timeout traducido a estado `unknown`/`pending`.
- Errores: usar `AppError` o subclases; en Presentation traducir a mensaje amigable (ver `05-errors.mdc`).

### UI
- Tailwind CSS y tokens `brand-*` del tema; tipografía definida en el Design System.
- Estados: loading, empty (sin issues), error/unknown con mensaje corto y no técnico.

### Tests
- Caso con proyecto “ordenado” (datos válidos) y caso con “bloqueos” o datos que simulen riesgo.
- Caso donde Jira falla o no responde: tarjeta en `unknown`/`pending` y resto del dashboard estable.
- Cobertura >= 80% en dominios/use cases e infraestructura involucrados.

### Dependencias / Paquetes
- No agregar dependencias nuevas salvo que esta HU lo indique explícitamente.
- Si hay 403/conectividad: detenerse, listar dominios necesarios, explicar por qué, no continuar.
